07_DECISIONS_LOG
=================
Key decisions, the reasons, and what was rejected. Argue with evidence if
you want to change one - then update this file in the same commit.

D1. Pure-TS domain layer
    Decision: the engine, types, import parsing and state rules live in
    src/domain with zero framework imports.
    Why: the 41 tests run in plain Node; the same code can later execute
    server-side (multi-user backend, AI proxy validation) unchanged.
    Rejected: putting reconciliation in React hooks/handlers - untestable
    without a browser and couples math to rendering.

D2. Adapter-as-external-store via useSyncExternalStore
    Decision: the data adapter exposes subscribe/load/update; React reads
    it through useSyncExternalStore with separate server snapshots.
    Why: avoids hydration mismatch between seeded server render and
    persisted client state, avoids setState-in-effect lint errors, and
    makes mode switching (demo/real) a pure adapter swap.
    Rejected: useState + useEffect hydration (caused both a lint failure
    and a real crash via an unbound subscribe method).

D3. Dual workspace modes instead of one mutable workspace
    Decision: demo (seeded) and real (empty onboarding) are separate
    storage keys, switched with a confirmation dialog.
    Why: judges get guided synthetic content while an operator's real
    records can never be polluted by demo data; "reset" semantics differ
    (reseed vs delete-with-typing-confirmation).
    Rejected: one workspace with a demo flag - too easy to mix data.

D4. Conservative summed uncertainty (no root-sum-square)
    Decision: interval bounds sum absolute input bounds; usage bound =
    start + end meter bounds.
    Why: inputs are correlated (same operator, same dipstick) so RSS would
    understate error; the sum is defensible and explainable to a jury.
    Rejected: RSS or confidence percentages - would imply calibration we
    do not have.

D5. Missing reading = no residual, ever
    Decision: incomplete status with named missing fields; no substitution,
    no nearest-reading borrowing (tolerance 0 in recon-v1.0).
    Why: substituting zero or a neighbor fabricates a balance - the exact
    failure mode the product exists to prevent. A tolerance option is on
    the backlog (P1-A) with explicit labeling.

D6. Duplicates are candidates, never auto-deletions
    Decision: exact + fuzzy detection links both records; a reviewer voids
    with a reason; voided rows persist; totals recompute.
    Why: same receipt + volume can be a legitimate re-record; auto-void
    would silently alter real records and could falsely accuse a supplier.

D7. Runs are immutable, superseded by newer runs
    Decision: corrections create a new run; old runs stay with a
    supersededByRunId pointer; run history is user-visible.
    Why: an audit trail that lets a reviewer see what the balance looked
    like BEFORE a correction - the core of "documented resolution".

D8. AI is opt-in, browser-direct, strictly schema-validated
    Decision: operator's own key, stored browser-locally; calls go directly
    to the configured provider; responses pass Zod schemas; failures fall
    back to rule-based text with a visible label; no AI in tests.
    Why: no server keys to leak in the static demo, the operator controls
    their own spend, and the deterministic engine never depends on a model.
    Rejected: shipping a shared key (leak risk + cost abuse) or embedding
    model output numbers into the record of truth.
    For shared deployments: docs/AI.md documents a server-side proxy
    (implemented only on a server-mode host, not in the static export).

D9. Static export as the demo target
    Decision: the public demo is a fully client-side static build.
    Why: zero server spend, no secrets, instant scale-out for judges; the
    app needs no backend until multi-user mode ships.
    Rejected: forcing server mode for the demo (deployment auth was not
    available and nothing server-side is needed yet).
    Quirk handled: scripts/fix-static-prefetch.mjs flattens Next 16.4.3's
    nested prefetch payloads to the names the router requests.

D10. Authorship identity
     Decision: every contributor commits under their own GitHub identity;
     a noreply address is preferred over a personal email.
     Why: links the work to real profiles and contribution graphs while
     keeping personal emails out of public history. The history shows the
     whole team (Arya-jannawar, Avani376, and the rest as they start
     pushing) - that is intentional, not an inconsistency.

D11. Mascot with motion discipline
     Decision: Bundu exists on every screen and reacts, but the trigger
     button is motion-stable (animation on an inner wrapper) and everything
     respects reduce-motion.
     Why: charm must not break accessibility or automation - Playwright
     refuses to click forever-animating elements, and so would some users.

D12. Demo seed includes a rich 14-day history site
     Decision: five seeded sites - four signature scenarios plus Riverside
     (35 records across two weeks) that exists to make the Dashboard
     charts meaningful.
     Why: signature scenarios must stay minimal and exact; charts need
     longitudinal data. Riverside reconciles its last complete day so its
     balance card is also honest.
